# Кейс: dantist45.ru — сайт частной стоматологической клиники

## Контекст

Частная клиника, один филиал в Екатеринбурге. Сайт я веду с 2015 года как
внештатный разработчик: сам выбираю стек, сам делаю, сам деплою.

Задача с самого начала была не про масштаб, а про **самостоятельность клиники**:
владелец и администратор должны менять услуги, тексты, контакты и объявления без
разработчика. Нагрузка небольшая — порядка 100 посетителей в сутки, — поэтому
все архитектурные решения принимались под «дешёво в эксплуатации и просто
в обслуживании», а не под высокую нагрузку.

## Как менялся стек

| Период | Стек | Что сделано |
|---|---|---|
| до 2015 | Kohana | исходный сайт клиники |
| 2015–2025 | Laravel + MySQL | полный рерайт; собственная админка: заявки с сайта, новости, контакты, служебные тексты. Лёгкий аналог CMS, а не полноценная |
| 2026 | Next.js 16 + React 19 + SQLite | перенос в продакшен на текущем стеке: публичная часть, админка, API |
| 2026 | TanStack Start + Prisma + PostgreSQL | параллельная реализация того же сайта — учебный проект на пару вечеров, чтобы разобрать фреймворк руками |

Важно: TanStack Start — **не миграция продакшена**, а вторая реализация для
изучения технологии. В продакшене с 2026 года работает версия на Next.js.

За 11 лет сменилось четыре поколения стека, и каждый раз это был не «перепишем
потому что модно», а «текущий вариант упирается в эксплуатацию».

## Что умеет админка

- Услуги и категории услуг — CRUD, сортировка, публикация
- Объявления / новости на главной
- Контактные данные и служебные настройки сайта (key-value в `settings`)
- Пользователи с ролями `admin` и `manager`
- Авторизация: сессия + bcrypt-хеши паролей, защита раздела через layout

Публичная часть — главная и каталог услуг; всё остальное тянется из базы,
поэтому контент меняется без деплоя.

## Архитектура

```
app/
├── (public)/          # route group: публичные страницы
│   ├── page.tsx
│   └── services/
├── admin/
│   ├── login/         # вход
│   └── (authenticated)/   # защищённая группа: dashboard, services,
│                          # categories, announcements, users
├── api/               # auth, categories, services, settings, users
lib/
├── db.ts              # better-sqlite3, подготовленные запросы
├── auth.ts            # сессии и проверка ролей
└── password.ts        # bcrypt
```

- **Route groups** разделяют публичную и админскую части на уровне роутинга,
  а не проверками внутри страниц.
- **API routes** дают один контракт для админки и для будущего мобильного
  клиента: `GET/POST /api/services`, `/api/categories`, `/api/settings`.
- **SQLite (better-sqlite3)** выбран осознанно: один сервер, один писатель,
  ~100 посетителей в сутки. Ноль администрирования, файл базы — это и есть
  бэкап. Postgres здесь был бы инфраструктурой ради инфраструктуры.
- **Docker + Caddy** на VPS: `docker compose up -d --build`, Caddy держит TLS,
  база вынесена в volume на хосте.

## Что получила клиника

- Контент меняется без разработчика — это была исходная цель
- Переезд на современный стек без простоя: адреса и структура страниц сохранены
- Предсказуемый деплой: один `docker compose`, без ручных правок на сервере

## Что бы я изменил

- **Пароль администратора по умолчанию** (`admin` / `admin123` в README) —
  должен генерироваться случайно при инициализации, а не задаваться в скрипте.
- **Нет миграций.** Схема создаётся скриптом `init-db`; при росте проекта нужен
  нормальный механизм версионирования схемы.
- **Нет тестов.** Как минимум API-роуты и проверку ролей стоит покрыть.
- **SQLite — один писатель.** Для одной клиники это не проблема, но решение
  осознанно привязано к масштабу: при появлении второй точки или интеграции
  с внешней системой переход на Postgres неизбежен.
- **Нет CI.** Сборка и деплой ручные, хотя проект уже контейнеризован — это
  следующий очевидный шаг.
